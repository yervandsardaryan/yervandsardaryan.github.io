Learning path 01 / 02

Requirements Analysis

From understanding the domain to eliciting requirements, resolving conflicts, managing change, and documenting an agreed solution.

01 / UNDERSTAND THE DOMAIN

Domain Knowledge & Use Cases

Requirements elicitation starts with understanding the relevant domain and the people who interact with the system. The material contrasts domain knowledge (static) with use cases (dynamic).

Domain knowledge

Rules, entities, terminology and constraints governing the problem area.

Use cases

Actor goals and interaction sequences describing system behavior.

Illustrative exampleCardless ATM withdrawal: account, withdrawal limit, and code-expiry policy are domain concepts; “Withdraw cash using a one-time code” is a use case.
02 / CLASSIFY THE NEED

Requirement Categories

The presentation distinguishes functional, non-functional, and system requirements, including behavioral processes, actors and functions versus usability, efficiency, performance and security constraints.

Functional

What the system must do or provide.

Non-functional

Qualities and constraints on system behavior.

Illustrative exampleFunctional: generate a one-time withdrawal code. Non-functional: verification response meets an agreed performance target. Neither target nor rule is copied from a real banking client.
03 / DISCOVER REQUIREMENTS

Elicitation Methods

The deck groups methods into traditional and modern techniques, contrasting simpler/low-risk elicitation with approaches that can require more effort.

Traditional methods
  • Structured and unstructured interviews
  • Questionnaires (multiple choice, rating, ranking)
  • Active and passive observation
  • Document analysis (forms, reports, regulations)
Modern methods
  • Prototyping (wireframes, Figma)
  • Brainstorming
  • Joint Application Development (JAD) workshops
  • Rapid Application Development (RAD) approach
Illustrative exampleFor a digital banking feature, interview operations, review withdrawal policies, observe ATM interactions, and prototype the mobile screen to validate assumptions.
04 / ALIGN & VALIDATE

Negotiation and Validation

The slides highlight out-of-scope requirements, a requirements dependency matrix, and explicit consideration of risks and priorities.

  • Risk examples: technical, performance, security and legal risks
  • Priority labels: high, medium, low, not sure
  • Dependencies: identify what must be available before another requirement can be delivered
Illustrative exampleA withdrawal-code feature depends on a secure code-verification service and ATM integration; its delivery priority can be negotiated alongside authentication and fraud controls.
05 / KEEP CONTROL

Requirements Management

The material identifies four practical concerns within requirements management:

  • Identify and classify requirements consistently
  • Organize requirements in parent–child relationships
  • Manage changes through proposals, negotiation, validation and documentation
  • Maintain traceability between requirements and other system artifacts
Illustrative exampleLink a 15-minute code-expiry rule to a feature, acceptance criteria, test cases and a change record, so its impact is understood when the policy changes.
06 / MODEL & RECORD

Business Model and Requirements Document

The deck includes requirements business model as an analysis topic and presents the requirements document as a tangible outcome of determining requirements.

A document may include functional/service statements, function requirements, data requirements and non-functional/constraint statements. The slides also mention names such as SRS, functional description and system requirements.

Illustrative structure (not a source template)Purpose → scope → stakeholders → business rules → functional and data requirements → non-functional constraints → assumptions → dependencies → traceability.

Learning path 02 / 02

BPMN 2.0 — Business Process Modeling

A shared visual language intended to help business analysts, developers, and business owners understand and communicate business processes.

01 / THE PURPOSE

Why BPMN?

The presentation introduces Business Process Model and Notation as a notation understandable to analysts drafting processes, developers implementing them, and the people managing or monitoring them. It references the Object Management Group (OMG) standards.

The slides also mention visualizing executable process definitions such as WSBPEL. This is historical context from the source, not a claim that all BPMN diagrams are executable.

03 / WORK & EVENTS

Activities and Events

The slides define an activity as work performed in a process. It can be atomic or compound. An event is something that happens during the process.

  • Start event — where a process begins
  • Intermediate event — something that occurs during execution
  • End event — where the process finishes
Illustrative exampleActivity: “Validate withdrawal code.” Intermediate event: “15-minute timer elapsed.” End event: “Withdrawal denied.”
04 / CONTROL THE PATH

Gateways

The source explains that gateways control how sequence flows converge and diverge. A gateway is appropriate where a decision or flow split/merge must be represented; not every connector needs one.

Validate code→◇ Code valid?→Approve / Reject
Illustrative exampleExclusive gateway: Yes → proceed with withdrawal authorization; No → show failure reason. The diamond with X is shown in the symbol reference above.
05 / RESPONSIBILITIES

Swimlanes

Swimlanes visually organize process activities by participating roles or organizational responsibilities.

Customer

Creates a cash-withdrawal request and enters a code at an ATM.

Bank systems

Validate and authorize the request.

Supplementary BPMN clarificationWithin the same pool, use sequence flows across lanes. Between distinct pools, use message flows to represent communication.
06 / SUPPORTING INFORMATION

Artifacts and Connectors

Artifacts add contextual process information; connectors express relationships or process flow. These headings appear in the source presentation, while the examples below are supplementary.

Artifacts

Data objects, text annotations and groups can clarify what the process handles.

Connectors

Sequence flows show order; message flows show communication; associations link relevant information.

Illustrative exampleAttach a withdrawal-request data object to “Generate code,” and use a dashed message flow between bank and ATM pools.

Governance & responsibility

Decision authority, reviews and RACI

Establish who can request, review, prioritize and approve requirements, along with how changes are communicated. BABOK describes governance in §3.3, and stakeholder responsibilities in §3.2. Its §10.39 Roles and Permissions Matrix concerns solution access rights, and should not be mistaken for an organizational RACI chart.

RACI is a complementary responsibility-assignment technique: R performs the work, A owns the outcome or decision, C provides input and I receives updates. It is not a separately named BABOK v3 technique.

ATM example: For approving a change to the one-time code expiry policy, identify a business owner accountable for approval; BA and security specialists may be responsible/consulted for analysis, while development and QA are informed or consulted according to governance.
BABOK v3: §§3.2–3.3, printed pp. 31, 37; §10.39, p. 333 · RACI explanation: supplementary
Requirements life cycle

Traceability and change impact

Trace a business need through individual requirements, design elements and tests. Forward and backward links help spot uncovered needs, unnecessary functionality, and consequences of a proposed change.

Illustrative trace: BR-ATM-02 (15-minute validity) → FR-07 (reject after expiry) → DAX/diagram or API rule → AC-07 (expiry boundary) → QA test TC-07.

When the expiry policy changes, inspect every linked requirement, API contract, UX message and test before approving the change.

BABOK v3: §5.1 Trace Requirements, printed p. 79; §5.4 Assess Requirements Changes, p. 91
Planning & uncertainty

Structured estimation techniques

Use estimates to discuss delivery effort, cost and uncertainty—not to imply certainty. BABOK identifies bottom-up, parametric, rough-order-of-magnitude, rolling-wave, Delphi and PERT approaches. Choose based on evidence, project phase and available experts.

Example PERT: Optimistic 3 days, most likely 5 days, pessimistic 11 days → (3 + 4 × 5 + 11) ÷ 6 ≈ 5.7 days. This is an illustrative planning estimate, not a commitment.

Communicate assumptions, dependencies and a range rather than just a single number.

BABOK v3: §10.19 Estimation, printed pp. 271–274
Risk management

Risk assessment and treatment

Describe risks using potential consequence, impact, likelihood and time frame. Identify reasonable responses, owners and triggers. Risk review belongs in both change strategy and day-to-day requirements discussions.

ATM example: An ATM times out after sending a dispense request. Risk: a customer may be charged without confirmed cash delivery. Control: distinguish pending from completed outcomes, log evidence and trigger reconciliation.
BABOK v3: §6.3 Assess Risks, printed p. 120; §10.38 Risk Analysis and Management, p. 329
Requirements quality

User stories, acceptance criteria and negative scenarios

Capture the actor, desired capability and business value in a concise story, then work with stakeholders to elaborate details. A story is a conversation starter—not a complete specification by itself. Add measurable acceptance criteria and both happy-path and exceptional scenarios.

Story: As a mobile banking customer, I want to request a cardless cash withdrawal so I can obtain cash without using my physical card.

Gherkin-style acceptance scenarios (supplementary BDD syntax). BABOK §10.48 mentions Given/When/Then as a common story format, but does not prescribe the formal Gherkin specification.

Scenario: One-time code expires after 15 minutes
Given a withdrawal code was generated 15 minutes ago
When the customer submits the code at an ATM
Then the withdrawal is rejected as expired
And no funds are debited

Scenario: Code cannot be redeemed twice
Given a code has already authorized a completed withdrawal
When the same code is submitted again
Then the system rejects the redemption
And no additional withdrawal is authorized

Scenario: Valid code within the time window
Given the customer has an active, unused withdrawal code
And the account has sufficient available funds
When the customer redeems the code before expiration
Then the bank may authorize the requested amount
And the code is reserved against concurrent redemption

Write acceptance criteria for authorization errors, boundary values, concurrency, retries and reversals, not only successful outcomes. Test cases should map back to a requirement or business rule.

BABOK v3: §10.48 User Stories, printed pp. 359–361; §10.1 Acceptance and Evaluation Criteria, pp. 217–220; §10.47 Use Cases and Scenarios, pp. 356–358; §7.2 Verify Requirements, p. 141 · Gherkin syntax examples: supplementary

Choose the right UML / process diagram

Elicitation & solution design

Prototyping practices

Use low-fidelity sketches to discover requirements quickly; use clickable or functional prototypes when workflow and interactions need validation. Clarify whether the prototype is throw-away or evolutionary so stakeholders do not mistake it for approved production design.

SketchReview with usersCapture feedbackReviseConfirm requirements
ATM example: Prototype a mobile page with amount, code, countdown and expired-state message. Test accessibility, error handling, wording and user understanding before defining the final interface.

Record assumptions, decision points and open questions; link approved behavior back to acceptance criteria.

BABOK v3: §10.36 Prototyping, printed pp. 323–326; §7.1 Specify and Model Requirements, p. 136
Artifact review

Verification versus validation

Verification: Is the requirement well formed, understandable, internally consistent and usable? Validation: Does it appropriately support the business need and stakeholder value?

Example: “The code expires quickly” is ambiguous (verification issue). “15 minutes” may be precise but still needs confirmation that it meets banking security and customer-access goals (validation issue).

Review checklist: clear actor, expected behavior, preconditions, business rules, exceptions, boundary conditions, security/performance constraints, dependencies, testability, source and approvals.

BABOK v3: §7.2 Verify Requirements, p. 141; §7.3 Validate Requirements, p. 144; §10.37 Reviews, p. 326
