Learning path 01 / 02

Requirements Analysis

From understanding the domain to eliciting requirements, resolving conflicts, managing change, and documenting an agreed solution.

01 / UNDERSTAND THE DOMAIN

Domain Knowledge & Use Cases

Requirements elicitation starts with understanding the relevant domain and the people who interact with the system. The material contrasts domain knowledge (static) with use cases (dynamic).

Domain knowledge

Rules, entities, terminology and constraints governing the problem area.

Use cases

Actor goals and interaction sequences describing system behavior.

Illustrative exampleCardless ATM withdrawal: account, withdrawal limit, and code-expiry policy are domain concepts; “Withdraw cash using a one-time code” is a use case.
02 / CLASSIFY THE NEED

Requirement Categories

The presentation distinguishes functional, non-functional, and system requirements, including behavioral processes, actors and functions versus usability, efficiency, performance and security constraints.

Functional

What the system must do or provide.

Non-functional

Qualities and constraints on system behavior.

Illustrative exampleFunctional: generate a one-time withdrawal code. Non-functional: verification response meets an agreed performance target. Neither target nor rule is copied from a real banking client.
03 / DISCOVER REQUIREMENTS

Elicitation Methods

The deck groups methods into traditional and modern techniques, contrasting simpler/low-risk elicitation with approaches that can require more effort.

Traditional methods
  • Structured and unstructured interviews
  • Questionnaires (multiple choice, rating, ranking)
  • Active and passive observation
  • Document analysis (forms, reports, regulations)
Modern methods
  • Prototyping (wireframes, Figma)
  • Brainstorming
  • Joint Application Development (JAD) workshops
  • Rapid Application Development (RAD) approach
Illustrative exampleFor a digital banking feature, interview operations, review withdrawal policies, observe ATM interactions, and prototype the mobile screen to validate assumptions.
04 / ALIGN & VALIDATE

Negotiation and Validation

The slides highlight out-of-scope requirements, a requirements dependency matrix, and explicit consideration of risks and priorities.

  • Risk examples: technical, performance, security and legal risks
  • Priority labels: high, medium, low, not sure
  • Dependencies: identify what must be available before another requirement can be delivered
Illustrative exampleA withdrawal-code feature depends on a secure code-verification service and ATM integration; its delivery priority can be negotiated alongside authentication and fraud controls.
05 / KEEP CONTROL

Requirements Management

The material identifies four practical concerns within requirements management:

  • Identify and classify requirements consistently
  • Organize requirements in parent–child relationships
  • Manage changes through proposals, negotiation, validation and documentation
  • Maintain traceability between requirements and other system artifacts
Illustrative exampleLink a 15-minute code-expiry rule to a feature, acceptance criteria, test cases and a change record, so its impact is understood when the policy changes.
06 / MODEL & RECORD

Business Model and Requirements Document

The deck includes requirements business model as an analysis topic and presents the requirements document as a tangible outcome of determining requirements.

A document may include functional/service statements, function requirements, data requirements and non-functional/constraint statements. The slides also mention names such as SRS, functional description and system requirements.

Illustrative structure (not a source template)Purpose → scope → stakeholders → business rules → functional and data requirements → non-functional constraints → assumptions → dependencies → traceability.
Source: “5.Requiremnts analysis.pptx” (8 slides). The topic coverage and categories above follow the presentation; explanatory wording, examples, and the illustrative document structure were newly authored for the website. Slides mentioning a “Requirements business model” do not specify its full modeling technique, so this guide does not invent one.
Learning path 02 / 02

BPMN 2.0 — Business Process Modeling

A shared visual language intended to help business analysts, developers, and business owners understand and communicate business processes.

01 / THE PURPOSE

Why BPMN?

The presentation introduces Business Process Model and Notation as a notation understandable to analysts drafting processes, developers implementing them, and the people managing or monitoring them. It references the Object Management Group (OMG) standards.

The slides also mention visualizing executable process definitions such as WSBPEL. This is historical context from the source, not a claim that all BPMN diagrams are executable.
02 / RECOGNIZE THE ELEMENTS

BPMN Symbol Quick Reference

The source organizes BPMN into activities, events, gateways, swimlanes, artifacts, and connectors. The drawings below are simplified learning illustrations.

ActivityWork carried out
EventSomething happens
GatewayControls branching
SwimlaneResponsibility grouping
03 / WORK & EVENTS

Activities and Events

The slides define an activity as work performed in a process. It can be atomic or compound. An event is something that happens during the process.

  • Start event — where a process begins
  • Intermediate event — something that occurs during execution
  • End event — where the process finishes
Illustrative exampleActivity: “Validate withdrawal code.” Intermediate event: “15-minute timer elapsed.” End event: “Withdrawal denied.”
04 / CONTROL THE PATH

Gateways

The source explains that gateways control how sequence flows converge and diverge. A gateway is appropriate where a decision or flow split/merge must be represented; not every connector needs one.

Validate code→◇ Code valid?→Approve / Reject
Illustrative exampleExclusive gateway: Yes → proceed with withdrawal authorization; No → show failure reason. The diamond with X is shown in the symbol reference above.
05 / RESPONSIBILITIES

Swimlanes

Swimlanes visually organize process activities by participating roles or organizational responsibilities.

Customer

Creates a cash-withdrawal request and enters a code at an ATM.

Bank systems

Validate and authorize the request.

Supplementary BPMN clarificationWithin the same pool, use sequence flows across lanes. Between distinct pools, use message flows to represent communication.
06 / SUPPORTING INFORMATION

Artifacts and Connectors

Artifacts add contextual process information; connectors express relationships or process flow. These headings appear in the source presentation, while the examples below are supplementary.

Artifacts

Data objects, text annotations and groups can clarify what the process handles.

Connectors

Sequence flows show order; message flows show communication; associations link relevant information.

Illustrative exampleAttach a withdrawal-request data object to “Generate code,” and use a dashed message flow between bank and ATM pools.
